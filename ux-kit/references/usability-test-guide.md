# 可用性测试方案设计指南（需求编写阶段）

本文档面向**需求编写阶段**的可用性评估（用户&专家）——通过邀请用户/专家对需求进行体验，验证其是否满足用户真实需求。供 ux-kit 的可用性模式（2C）与方案模式的可用性评估阶段（2D）生成"可用性测试方案"材料时使用。

> **分工说明**：通用可用性测试的样本量（Nielsen 范式）、样本特征、配额、实施流程仍以 `references/research-methods.md` 为准；本文档负责需求编写阶段测试方案的文档结构与任务卡设计。

---

## 一、方法概述
### 1.1 概念
需求编写阶段的可用性评估（用户&专家）是通过邀请用户/专家对需求进行体验，验证其是否满足用户真实需求的过程。

### 1.2 目的
以用户视角验证需求设计是否匹配用户需求、是否具备良好的可用性。

### 1.3 适用场景
适用于对客强交互类需求，或需求设计存在多方案、模糊点、争议点等情况。

### 1.4 步骤流程
1. **任务编制**：明确评估目标（希望通过评估为需求设计提供哪些支持）→ 明确评估清单（结合目标梳理需评估的任务清单）→ 编写任务卡（场景、任务明细、待探寻问题、预期结果等）→ 准备评估材料（待用户/专家体验的环境及数据）
2. **招募用户&专家**：用户招募选择目标用户群体中的代表性用户，确保能对需求产生共鸣；专家邀请具备产品相关领域专业经验的专家
3. **执行评估**：引导用户/专家逐条完成任务，记录其理解、反馈和疑问；使用观察笔记、录音或问卷等方式记录
4. **分析问题**：问题去重整合（分类汇总反馈，提取问题点和改进建议）→ 问题分级分类（按标准标注分类分级信息）→ 问题优化（在需求提交前完成）

---

## 二、注意事项（按阶段）
### 2.1 任务编制阶段
- 评估清单应重点关注**高频、新增、有疑问**的功能
- 测试任务需以**用户视角**编写，避免使用过于技术化或晦涩的语言
- 保证测试任务具有**针对性**，避免任务范围过宽导致反馈不聚焦
- 评估材料尽量基于**高保真动态原型**

### 2.2 招募用户&专家阶段
- 平衡数量：建议招募 **5-8 名用户和 2-3 名专家**，确保多样化的视角

### 2.3 执行评估阶段
- 告知用户评估的是**产品体验而不是用户能力**
- 重点观察用户完成任务**全流程**的行为
- 引导用户**出声思维**，表达出完成任务过程中的理解、反馈和疑问
- 可按需记录任务完成率、操作时间等**定量数据**

### 2.4 分析问题阶段
- 汇总时注意区分**用户共性问题和个性化意见**，避免以偏概全
- 分析问题时结合用户与专家的意见，**平衡可行性与用户体验需求**

## 三、任务卡设计
任务卡是测试方案的核心单元，每张卡包含：

| 项目 | 内容 |
|------|------|
| 场景 | 描述用户使用场景 |
| 任务步骤 | 拆解为具体任务步骤 |
| 探寻问题 | 针对该任务要验证/探寻的问题 |
| 完成标准 | ✓ 成功（没有帮助的情况下完成）<br>○ 成功有困难（需要1-2次提示）<br>○ 失败（需要2次以上帮助） |
| 参与者打分 | 用户主观评分 |

**任务卡编写要点**：

- 任务说明引导用户"边做边说"（出声思维），如"您在操作的过程中可以告诉我您准备做什么、在看哪一部分、会做什么操作"
- 关注点/问题按任务环节拆表记录（如：观察页面 → 操作流程 → 结果确认）
- 每个环节后设置**过渡提问**衔接下一任务或深挖体验（如"假设您已经成功签订计划，您接下来会想了解什么？"）
- 探寻问题覆盖四类：**理解度**（能否看懂功能用途）、**操作效率**（能否顺利完成任务）、**方案对比**（两个设计方案哪个更好）、**预期差异**（与用户期望的差距）

## 四、实战案例摘要（心愿定投可用性测试）
以"心愿定投"功能为例展示任务卡拆解思路：

| 任务 | 任务说明要点 | 关注点示例 |
|------|-------------|-----------|
| 任务一：功能页面观察 | 观察页面后回答问题（不操作） | 能否看出功能用途；心愿设定入口是否吸引自主填写；结束后过渡问是否在其他 App 用过类似功能 |
| 任务二：定投协议签订 | 按自己期望设定心愿、挑选产品完成定投（边做边说） | 心愿设定是否吸引/会否直接退出；选品时重点看什么信息；两种选品方案哪个更好；怎么理解测算收益率；确认页信息是否过多或缺失 |
| 任务三：定投持仓及心愿查询 | 在持仓页查找自己关注的信息 | 信息是否有缺失（如交易明细入口）；心愿外露信息是否满足需求；达成后分享欲；在途交易多类型混排是否需要筛选；月度账单期望看到哪些统计 |
| 任务四：查看/修改/终止定投计划 | 依次执行查看、修改、终止 | 查看时主要看什么、对信息有无疑问；修改时是否预期同步修改心愿目标；终止后是否有疑惑（到底终止了没有、下期还扣款吗、之前的钱去哪儿了） |

**要点**：每个任务含"任务说明（引导话术）+ 按环节拆分的关注点表 + 结束后过渡提问"；探寻问题围绕理解度、效率、方案偏好、预期差异四类展开。

## 五、生成测试方案时的规则
- 方案文档结构按 `templates/usability-test.md`：测试目标 → 开场白 → 测试前调研（可选）→ 测试任务（任务卡）→ 总结回顾 → 结束语 → 附录记录表
- **测试目标**与任务及探寻内容必须有明确对应（用勾选式列出）
- **开场白**必须包含"评估的是产品不是用户能力"声明
- **总结回顾**固定两个问题：功能中最好的方面、最差的方面
- 样本设计按 `research-methods.md` 的可用性评估规则；需求编写阶段默认 5-8 用户 + 2-3 专家
- 嵌入眼动测试时，在任务说明中注明同步采集视线数据，规则见 `references/eye-tracking.md`
