# UX 研究工具箱 (ux-kit)

## 设计目标

用户用一句话提出研究诉求，ux-kit 自动判断产出内容：**明确要问卷就直接产出问卷，明确要访谈提纲就直接产出提纲，明确要可用性测试方案就直接产出测试方案**；诉求模糊或涉及多种材料时，先产出研究方案供用户确认，确认后再按阶段产出对应材料。所有产出前都经过"研究问题陈述 → 用户确认"环节，确保方向正确。

## 整体流程

```
用户一句话
    ↓
Phase 0: 输出模式识别（问卷 / 提纲 / 可用性 / 方案）
    ↓
Phase 1: 问题澄清（按模式差异化追问 → 研究问题陈述 → 用户确认）
    ↓
Phase 2: 按模式产出
  ├─ 2A 问卷模式   → 完整问卷
  ├─ 2B 提纲模式   → 完整访谈提纲
  ├─ 2C 可用性模式 → 完整可用性测试方案
  └─ 2D 方案模式   → 研究方案 → 用户确认 → 按阶段生成材料
    ↓
输出：DOCX 文档（转换失败时降级为 Markdown），按模式命名保存至 outputs/
```

## Phase 0: 输出模式识别

### 产物词判定

从用户输入中识别产物意图，判定产出模式：

| 输入信号 | 模式 |
|---------|------|
| 含"问卷/调查表/量表/问卷编制/满意度问卷"等 | **问卷模式** |
| 含"访谈/访谈提纲/访谈大纲/深度访谈"等 | **提纲模式** |
| 含"可用性测试/可用性评估/易用性测试/测试方案/眼动测试/眼动"等 | **可用性模式** |
| 含"研究方案/调研方案/用户研究/研究/调研"或**无明确产物词** | **方案模式**（默认） |
| 同时含多种产物词（如"问卷和访谈都做"） | **方案模式** |

### 方法信号路由

用户直接指定方法且未提及其他材料时，按方法默认归属的模式进入：

| 方法信号关键词 | 路由模式 | 原因 |
|-------------|---------|------|
| Kano/卡诺、ETS/体验评估/体验诊断 | 问卷模式 | 以问卷为采集方式 |
| JTBD/用户决策、灵犀旅程/体验旅程、卡片分类/信息架构 | 提纲模式 | 以访谈为主要采集方式 |
| 眼动/眼动测试/视觉注意/热图 | 可用性模式 | 眼动是可用性评估的同步采集技术 |
| 用户画像/用户角色 | 方案模式 | 画像需要多阶段综合产出 |

**路由优先级**：用户同时说了产物类型 → 以产物类型为准（如"做个Kano访谈"→提纲模式）；说了多个方法或"研究""规划"等 → 方案模式。

### 模式切换

- 澄清过程中用户修正产物意图（"其实我只要问卷"）→ 切换模式重新澄清
- 判定困难时默认方案模式（安全兜底）

## Phase 1: 问题澄清

把用户模糊的一句话变成一句清晰的研究问题。允许多轮交互，但**不做固定剧本**——输入已足够清晰时少问或不问。

### 触发条件

| 信号 | 示例 |
|------|------|
| 研究目标过于宽泛 | "用户还有什么需求" |
| 核心概念模糊未定义 | "体验怎么样" |
| 多个问题混在一起 | "满意度和使用习惯和新功能接受度" |
| 只给了动作没有方向 | "帮我调研一下这个产品" |

**不触发**：用户输入已包含清晰的研究对象 + 目标人群 + 研究意图，直接进入产出流程。

### 交互方式

每轮使用 `question` 工具与用户交互，设置 `multiple: true` 和 `custom: true`。选项不加前缀，选项末尾始终包含"跳过此问题"和"其他（请描述）"兜底项。选项措辞参考 `references/question-templates.md`，模板未覆盖的场景根据用户原话自由设计。

> `question` 工具不可用时，改用纯文本提问，选项前加 `A. B. C. D.` 字母序号，格式为"请选择/补充（输入字母即可）：A. ... B. ... C. 其他（请描述）"。

### 澄清维度（按模式差异化）

| 维度 | 方案模式 | 问卷模式 | 提纲模式 | 可用性模式 |
|------|---------|---------|---------|-----------|
| 研究方向 | 模糊时必问 | 必问（调研主题） | 必问（访谈目标） | 必问（测试目标） |
| 研究动机/决策背景 | 决策场景必问 | 可省 | 可省 | 可省 |
| 目标人群 | 必问 | 必问 | 必问 | 必问（目标用户） |
| 聚焦范围 | 可聚焦时问 | 可省 | 可省 | 必问（评估对象/功能范围） |
| 约束条件 | 有压力才问 | 有压力才问 | 时长/线上必问 | 原型/时长必问 |
| 设计模式/模型 | 自动匹配 | 自动判断（见 2A） | 不适用 | 不适用 |
| 产品/话题背景 | 方案层推断 | 可省 | 必问 | 必问（待体验的功能） |

> 设计模式/模型（Kano/ETS/量表）与嵌入技术（JTBD/卡片分类等）一律**自动判断**，不追问用户；用户主动指定时尊重用户指定。

### 追问策略

1. 回顾用户已有输入，标记缺口
2. 从缺口中挑**最重要的一个**发问，一次只问一个核心维度
3. 用户回答后，先做一句话总结确认，再更新缺口清单
4. 重复，直到剩余缺口不影响产出。大多数情况 3-5 轮收工

**主动追下去**：回答仍比较泛；跳过了影响产出的维度。**可以少问**：初始输入已覆盖大部分维度；用户"你帮我定"。**停止条件**：关键信息已明确；再问边际收益低。

### 输出：研究问题陈述（必须确认）

澄清完成后输出研究问题陈述并请用户确认：`## 研究问题陈述` + `[一句概括：研究对象 + 目标人群 + 研究意图]` + `以上理解是否正确？确认后我将开始生成。`

**必须等待用户明确确认后才能进入 Phase 2**。若用户提出修改意见，按修改更新后再请确认。多轮后仍不清晰时，输出当前最接近的解读并标注"存在不确定性"。

## Phase 2: 按模式产出

### 2A 问卷模式 → 完整问卷

按 `templates/questionnaire.md` 填充，生成完整问卷。

#### Step A: 需求分析与模式识别

**A1 设计模式**：

| 设计模式 | 判定条件 | 设计路径 |
|---------|---------|---------|
| **量表驱动型** | 已有维度/指标框架，需量化测量 | 维度→指标→题目，输出测量框架表 |
| **开放探索型** | 发现痛点、收集建议，不预设维度 | 按信息需求分模块，开放题为主 |
| **方法论驱动型** | 指定了具体方法论（Kano、ETS 等） | 遵循方法论规则设计对应模块 |
| **混合型** | 以上多种模式组合 | 分区设计，各走各的路径 |

**A2 模型判断**：

| 信号关键词 | 模型 | 参考文件 |
|---|------|---------|
| "功能优先级""需求分类""Kano" | **Kano** | `references/kano-model.md` |
| "满意度""体验评估""体验诊断""ETS" | **ETS**（ETS-U/ETS-E） | `references/ets-model.md` |
| "通用调研" | **通用** | `references/question-design.md` |
| 多目标混合 | **混合** | 组合多个模型模块 |

A3 ETS 子模式选择见 `references/ets-model.md` 第四章。A4 按判断结果读取对应参考文件。

#### Step B: 问卷结构设计

按模板骨架组织：设计说明 → 指导语 → 甄别题 → 主体问卷 → 结语。

- **甄别题**：筛选目标被访者，跳转逻辑 inline 标注
- **人口统计学**：用作分组筛选时放甄别题之后、仅事后分类时放最后，标题统一用"基本信息"
- **测量框架表**（量表驱动型）：输出「维度→指标→操作化定义→对应题目」映射表；每指标至少 2 题，每维度 3-5 题
- **逻辑控制**：跳转/展示逻辑 inline 标注在题目/选项旁，复杂时附录汇总表

#### Step C: 题项编写

题项表述规范（一题一问、具体可感知、中性表述、避免否定嵌套、不预设前提）与选项设计原则（互斥、穷尽、平衡、特异）的完整正反例表见 `references/question-design.md`，生成时逐题对照检查。

**按模型选择题型**（完整规则以对应参考文件为准）：
- 通用问卷：见 `references/question-design.md`；开放题 ≤ 3 题，提供思考锚点
- Kano：正反双题，详见 `references/kano-model.md`
- ETS-U/ETS-E：详见 `references/ets-model.md`；题项表述适配规则（最小改动原则、不可动条款、兜底场景）见该文件 5.4-5.5 节

#### Step D: 附录

- **数据分析计划**：ETS 问卷写 ETS 得分计算和体验优化矩阵；其他问卷按分析目的列出方法、涉及题目和预期产出
- **质量控制建议**：预测试 3-5 人认知访谈、无效问卷标准、信效度要求（Cronbach's α ≥ 0.7，量表驱动型）

### 2B 提纲模式 → 完整访谈提纲

按 `templates/interview-guide.md` 填充，生成完整提纲。

#### Step A: 确定话题模块

1. 研究问题陈述中已给出话题结构的，以其为准
2. 否则自行拆解 3-5 个核心话题，顺序：简单→复杂、具体→抽象
3. 每个话题模块约 10-20 分钟；开场暖场和收尾也是独立模块

#### Step B: 识别嵌入技术

| 嵌入技术 | 匹配信号 | 对提纲的影响 | 参考文件 |
|---------|---------|-------------|---------|
| JTBD | 涉及用户选择/切换/决策 | 该模块按决策链展开 | `references/jtbd-framework.md` |
| 灵犀旅程 | 涉及端到端体验/旅程 | 该模块按旅程五要素展开 | `references/journey-mapping.md` |
| 卡片分类 | 涉及信息架构/导航分类 | 访谈后加入分类任务（约15分钟） | `references/card-sorting.md` |

#### Step C: 提纲主体——分级结构 + 四列表格

每个话题模块是一个章节标题，标题下用斜体写核心目标（一句话），然后是四列表格（维度/核心问题/追问/执行要点）：

- **核心问题列**：锚定具体事件、开放不引导、一次一问、先事实再感受再看法
- **追问列**：用 `→` 表示递进
- **执行要点列**：访谈员现场操作指引，写白话不写术语；探询技术翻译为白话时参考 `references/probing-techniques.md`

**执行要点写法原则**：给具体可操作的白话指令（"如果用户说 XX，可以试试问 YY"），不解释题目设置目的、不写专业术语。

**题目内部用 CBA 原则组织（C-情境→B-行为→A-评估），详见 `references/cba-framework.md`；CBA 是设计工具，不在产出中输出标签。**

#### Step D: 概述与附录

提纲开头写概述：**预计时长**、**提纲设计思路**（陈述用到的方法与设计逻辑）。末尾附**使用说明**：访谈前准备、执行注意事项（时间把控、录音检查、访谈礼仪、记录要点、结束动作）。**研究背景与目标、被访者画像已由澄清/方案部分覆盖，不在提纲概述中重复。**

### 2C 可用性模式 → 完整可用性测试方案

按 `templates/usability-test.md` 生成，方法规则与任务卡设计详见 `references/usability-test-guide.md`。

- **测试目标**：勾选式列出，与任务及探寻内容有明确对应
- **任务卡设计**（每任务一张卡：场景/任务步骤/探寻问题/完成标准/参与者打分）：关注高频、新增、有疑问功能；任务以用户视角编写；完成标准三分法（✓成功/○有困难/○失败）；探寻问题覆盖理解度、操作效率、方案对比、预期差异
- **涉及眼动测试时**：任务卡设计参考 `references/eye-tracking.md` 需求编写流程，数据采集归属见该文件第九节
- **开场白与结束语**：使用模板标准话术，开场白**必须包含"评估的是产品不是用户能力"声明**
- **附录**：任务记录表（耗时/提示次数/是否成功/参与者打分）

### 2D 方案模式 → 研究方案 → 确认 → 材料

#### Step A: 需求解析

1. **研究类型**：探索型 / 测量型 / 评估型 / 描述型
2. **研究子目标拆解**：一句话需求拆解为具体子目标
3. **约束条件**：时间紧迫程度、可及样本规模、有无实验室设备

#### Step B: 层级式方法匹配

**先选数据采集方式 → 再选嵌入技术 → 合并同类阶段。**

主采集方式匹配与嵌入技术匹配的完整规则见 `references/research-methods.md` 各方法的"数据采集归属"小节。关键规则：

- 每个研究阶段以一种数据采集方式为锚点
- 嵌入技术归入对应主采集方式，不独立成阶段（卡片分类样本量≥15人时可独立）
- 同一主采集方式承载多个嵌入技术时合并为一个阶段
- 阶段数 ≤ 4

**读取参考文件**：四种采集方式 → `references/research-methods.md`；各嵌入技术 → 对应参考文件；样本量精确计算 → `references/sample-size-calculator.md`。

#### Step C: 产出研究方案（纯方案）

按 `templates/research-plan.md` 生成**纯方案文档**（不含完整材料，材料位置写内容概述）→ **必须等待用户确认方案**。模板内含六部分结构及各部分生成指引。

**方案确认**：用户确认后进入 Step D；若用户提出修改，按修改更新方案后再确认。

#### Step D: 生成研究材料（确认后）

用户确认方案后，按阶段生成材料，**每份材料一个文件**：

| 阶段采集方式 | 生成文件 | 生成规则 |
|------------|---------|---------|
| 用户访谈 | `outputs/[主题]访谈提纲.docx` | 2B 提纲规则全流程 |
| 问卷调查 | `outputs/[主题]问卷.docx` | 2A 问卷规则全流程 |
| 可用性评估 | `outputs/[主题]可用性测试方案.docx` | 2C 可用性规则全流程 |
| 用户声音分析 | 内嵌方案文档 | 声音分析计划 |

材料生成后执行对应质量检查清单（详见 `references/quality-checklists.md`），并告知用户全部文件路径。

## 输出与保存

- 所有产出**正常为 DOCX 文档**；DOCX 转换失败时降级为 Markdown 交付
- 产出流程：生成 Markdown 内容 → 调用转换脚本生成 `.docx`（脚本内部按 JSON 协议渲染，全文微软雅黑、标题深蓝样式）→ 验证 docx 存在 → **删除中间 `.md`** → 报告 docx 路径
- 转换命令：`python scripts/convert_to_docx.py outputs/[主题]XX.md outputs/[主题]XX.docx`（脚本路径相对技能根目录；样式全部代码内控制，不依赖外部模板）
- 文件命名：`[主题]问卷.docx` / `[主题]访谈提纲.docx` / `[主题]可用性测试方案.docx` / `[主题]研究方案.docx`；用户指定路径时按用户要求
- 转换失败时：保留 `.md` 文件作为降级交付物，报告 md 路径并说明原因
- 生成后在对话中告知 docx 路径，并附核心设计决策摘要（模式选择、方法组合、阶段序贯、关键设计点）

## 异常处理

- **参考文件缺失时**：跳过该技术的嵌入，用通用规则继续产出，在产出中标注"未启用XX方法（参考文件缺失）"
- **用户请求超出支持方法范围**：说明支持的方法清单，给出替代建议，不强行套用不匹配的方法
- **`question` 工具不可用时**：改用纯文本提问，选项前加 `A. B. C. D.` 字母序号，格式为"请选择/补充（输入字母即可）：A. ... B. ... C. 其他（请描述）"
- **用户多次修改仍不满意**：输出当前版本 + 标注"存在不确定性"，请用户直接在文档上修改
- **产出质量自检不通过时**：标注问题项，给出修改建议，不静默交付有问题的内容
- **DOCX 转换失败时**：转换脚本渲染失败则保留 `.md` 文件作为降级交付物（脚本退出码非 0），告知用户"DOCX 转换未成功，已提供 Markdown 文件，可手动转换或复制到 Word 中编辑"

## 全局策略

### 多角色处理

- **默认**：一套材料，通过基本信息区分角色
- **角色差异大**：访谈提纲核心题目不变、"执行要点"按角色微调；问卷拆分为多套、核心量表保持一致

### 特殊场景处理

| 场景 | 处理方式 |
|------|---------|
| 资源极度有限（1-2 天） | 轻量方法：5 人快速访谈 + 嵌入卡片分类、在线问卷 |
| 涉及多个用户群体 | 按群体分别设计样本特征和配额 |
| B 端产品研究 | 样本量适当下调，注重决策链角色覆盖，涉及决策话题用 JTBD 逻辑 |
| 访谈时长受限（≤30 分钟） | 聚焦 1-2 个核心话题，每话题精简到 2-3 题 |
| 有前置数据/访谈发现 | 背景中引用；问卷优先从访谈发现提取维度并标注来源 |

### 常见错误提醒

- 不要套用同一结构——先做模式识别与方法匹配，再差异化设计
- 问卷模式：模型判断自动完成，不问用户；Kano 正反题必须配对；ETS 条数与映射结构保留
- 访谈提纲不要出现 CBA/JTBD/ORID 等专业术语——那是内部工具，不是给访谈员看的
- 澄清输出研究问题陈述后必须等用户确认，确认前不得继续
- 访谈问题是探针不是选择题；问卷题目不是访谈探针，两者写法不可互换
